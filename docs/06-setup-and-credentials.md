# 06 — Setup and credentials

> Status: **draft v0.1** · 2026-10-16
> What to create, where each value goes and when it is needed, so the implementing agent never has to stop and ask for a key. The variable names live in [`.env.example`](../.env.example), the single source of truth. Markers: ◐ read in the vendor's own docs while researching; △ from memory or a secondary source, so check it when you create the resource.

## 1. The short version

- **To start you need three values:** an Anthropic key for a `dev` workspace, and the publishable and secret keys of a Clerk development instance. Everything else a local setup needs has a default (Postgres in Docker, MinIO standing in for R2) or is generated by the agent.
- Copy `.env.example` to `.env`, fill the three `[YOU-now]` lines and run the check in [§6](#6-checking-it).
- **What each token may do** is written above it in `.env.example` and tabulated in [§3.9](#39-scopes-and-permissions-per-token). Grant exactly that and nothing more.
- **Cloudflare, servers, observability and the rest wait for staging** (P0-09 and P0-10, about week 2). Create them then, or all at once if you prefer. Each `[YOU-...]` tag in `.env.example` says when.
- **Where values live.** Local values go in `.env`. Staging and production values go in `.env.staging` and `.env.production` on your machine (gitignored by `.env.*`) and in the GitHub environment secrets. Nothing secret goes in git, in a chat message, or in a `VITE_` variable, because those ship to the browser.
- The agent runs on your machine, so it reads `.env` directly and can use your logged-in tools (Docker, `wrangler`, `gh`).

## 3. Services

### 3.1 Anthropic

Create four workspaces in the Console, one key each. Each has a monthly spend limit that sits behind our own budgets as the last backstop ([D-18](05-decisions.md#d-18-who-pays-for-tokens-managed-credits-or-bring-your-own-key)).

| Workspace | Used by | Limit per month | Key goes to |
|---|---|---|---|
| `dev` | local development and benchmarks | $50, raised for a paid sweep ([D-22](05-decisions.md#d-22-cheap-first-testing-ladder)) | `ANTHROPIC_API_KEY` in `.env` |
| `ci` | live model calls in GitHub Actions, only if a test ever needs them (CI runs in replay mode, [D-22](05-decisions.md#d-22-cheap-first-testing-ladder)) | $25 | the CI secret `ANTHROPIC_API_KEY`, created only then |
| `staging` | the staging app | $100 | `.env.staging` |
| `production` | the production app, managed credits | $500 (the private beta is capped at about $375 a month) | `.env.production` |

- Only `dev` is needed to start. Create `staging` and `production` when those environments exist, and `ci` only if a test ever needs live calls in CI.
- **Plan credit.** Your Max plan gives $200 a month of API credit, which pays for any key in the Console organization linked to it, so create `dev` there. The credit doesn't roll over, and every workspace in that organization draws from one balance, so keep production in a separate organization ([D-21](05-decisions.md#d-21-testing-on-the-first-party-api-self-funded)).
- Creators' own keys (BYOK) are never in `.env`. They sit encrypted in Postgres under `SECRETS_MASTER_KEY` ([architecture §11a](03-architecture.md#11a-model-access-managed-credits-or-byok)).
- `ROUTING_PROFILE` starts at `dev-cheap` and `LLM_MODE` at `live` ([D-22](05-decisions.md#d-22-cheap-first-testing-ladder)).
- **Model names.** The native Anthropic API, called directly or through the gateway's `/anthropic` endpoint, takes `claude-opus-5-5`. Cloudflare's REST endpoints use `provider/model` names, so the same model is `anthropic/claude-opus-5.5` there. That dotted spelling is the founder's: Cloudflare's docs show `anthropic/claude-sonnet-5` and `anthropic/claude-sonnet-4` but no 5.5 model ◐, so it is △ until `cfctl doctor` resolves it. The routing profiles use the native ID and `apps/server/config/routing/models.yaml` maps each one to its Cloudflare name ([architecture §7.5](03-architecture.md#75-model-routing-sub-agents-and-benchmarking)). The REST path also needs its own token, `CF_AI_API_TOKEN` ([§3.9](#39-scopes-and-permissions-per-token)), and credits loaded in Cloudflare. Claude stays on the native path by default ([D-19](05-decisions.md#d-19-model-gateway-cloudflare-ai-gateway-in-byok-mode-openrouter-optional)).
- `ANTHROPIC_BASE_URL` stays empty until the gateways exist (P0-09). After that every environment sets its gateway's URL, `cf-dev` for local, CI and benchmarks ([§3.3](#33-cloudflare-needed-from-p0-09)). Empty again means a direct call, the bypass for debugging.
- **Spend caps and limits (P4-00a).** Every model call goes through `internal/agents/llm`, which refuses a call before sending it when it could break a cap, and writes one `usage_ledger` row per call (`billed_to` is `test` in local, ci and bench, and `platform` in staging and production). Money is in micro-dollars (1,000,000 = $1). The prices come from `apps/server/config/pricing/`, one dated file per version.

  | Variable | Default | What it does |
  |---|---|---|
  | `LLM_MAX_REQUEST_MICROS` | 2000000 ($2) | Refuses any single call whose worst case is above it. The worst case is the counted input tokens at list price (a cache write if the request has cache breakpoints) plus `max_tokens` of output. A cheap local bound is used when it clears the cap, so most calls need no `count_tokens` round trip |
  | `DAILY_SPEND_CAP_MICROS` | 20000000 ($20) | Per workspace and UTC day, summed from `usage_ledger`. A call is refused when today's spend plus its worst case is over the cap. A per-run budget is passed in by the agent runtime |
  | `LLM_KEY_CONCURRENCY` | 4 | Requests in flight per API key. More callers wait in a queue. On 429, 529 and 5xx answers the client backs off with jitter and honours `retry-after`; nothing else retries |
  | `LLM_ALLOW_UNPRICED` | empty | `1` lets a model with no price in the table run (ledger cost 0, caps cannot be checked). Empty refuses it |
  | `LLM_CASSETTE_DIR` | `testdata/cassettes` | Where `LLM_MODE=record` writes and `replay` reads cassettes (`<dir>/<stage>/<key>.json`) |

  `cfctl llm ping --stage editor [--profile v1-start]` checks all of this without cost (it only counts tokens); add `--live --workspace wks_…` to send one tiny message and show its ledger row.

### 3.2 Clerk

1. Create an application and turn on **Organizations**, Clerk's B2B side. Every workspace is a Clerk organization, and a solo creator gets a personal one at onboarding ([D-12](05-decisions.md)). Set **Membership required** (the label may read differently; it is the setting that turns personal accounts off) so every signed-in user has an active workspace △. Keep the default roles, Admin for the creator and Member for a teammate. Add custom roles only when the Team and Agency plan needs them, because they may need a paid Clerk plan.
2. Use the **development instance** for local work and staging. Copy the publishable key (`pk_test_…`) into `VITE_CLERK_PUBLISHABLE_KEY` and the secret key (`sk_test_…`) into `CLERK_SECRET_KEY`. The TanStack Start SDK reads exactly these two names ◐ (`@clerk/tanstack-react-start`).
3. **The secret for the Go backend is `CLERK_SECRET_KEY`, so there is nothing extra to create.** The Clerk Go SDK middleware uses it to fetch the instance's public signing keys and verify each request's session token, and the same key lets the backend call Clerk's Backend API. Keep it server-side only: never in the browser, so never with a `VITE_` prefix.
4. **Webhook, on staging.** Add an endpoint `https://api-staging.contentfabrique.app/v1/webhooks/clerk` and subscribe it to these nine events and nothing else: `user.created`, `user.updated`, `user.deleted`, `organization.created`, `organization.updated`, `organization.deleted`, `organizationMembership.created`, `organizationMembership.updated` and `organizationMembership.deleted`. Copy its signing secret (`whsec_…`) into `CLERK_WEBHOOK_SECRET`. Locally the handler is tested with signed fixtures, so no tunnel is needed (see "Locally" below).
5. **Production instance, later.** It is tied to `contentfabrique.app`: Clerk lists the DNS records to add in Cloudflare △, and its webhook endpoint is `https://api.contentfabrique.app/v1/webhooks/clerk`. It gives `pk_live_…` and `sk_live_…` keys.

**Locally, without webhooks.** Clerk cannot reach a laptop, so on localhost nothing delivers `user.created` or `organizationMembership.created`. The API makes up for it **just in time**: the first authenticated request of a user and organization that are not in Postgres yet fetches them from Clerk's Backend API (with `CLERK_SECRET_KEY`: the user's email, the organization's name), and creates the user, the workspace and the membership. The role comes from the session token (`org:admin` is `owner`, `org:member` is `editor`, any other role is `viewer`). So signing in on `http://localhost:3000` and opening Settings is enough: it shows the `GET /v1/me` data, and the rows exist afterwards. The same path covers a webhook that was missed on staging. A user or organization deleted in Clerk stays refused: the API answers 403 `user_deleted` or `workspace_deleted` even for a token that has not expired yet, and a user removed from an organization gets 403 `not_a_member` for tokens issued before the removal.

**Testing the webhook endpoint by hand.** Set `CLERK_WEBHOOK_SECRET` to any `whsec_` plus base64 text (for example `whsec_` and the base64 of 32 random bytes), start the API, and post a fixture signed with it. A signature is `v1,` plus base64 of HMAC-SHA256 over `<svix-id>.<svix-timestamp>.<body>` with the decoded secret, sent with the headers `svix-id`, `svix-timestamp` (Unix seconds, at most five minutes old) and `svix-signature`:

```python
# sign.py: python3 sign.py msg_local_1 '<body>'   (CLERK_WEBHOOK_SECRET in the environment)
import base64, hashlib, hmac, os, sys, time, urllib.request
msg_id, body = sys.argv[1], sys.argv[2].encode()
key = base64.b64decode(os.environ["CLERK_WEBHOOK_SECRET"].removeprefix("whsec_"))
ts = str(int(time.time()))
sig = base64.b64encode(hmac.new(key, f"{msg_id}.{ts}.".encode() + body, hashlib.sha256).digest()).decode()
req = urllib.request.Request("http://localhost:8080/v1/webhooks/clerk", data=body,
    headers={"svix-id": msg_id, "svix-timestamp": ts, "svix-signature": "v1," + sig})
print(urllib.request.urlopen(req).read().decode())
```

A body to try: `{"type":"user.created","timestamp":1760000000000,"data":{"id":"user_x","primary_email_address_id":"idn_1","email_addresses":[{"id":"idn_1","email_address":"x@example.com"}],"updated_at":1760000000000}}`. The automated tests sign with the Svix library (`internal/auth/webhook_test.go`). The answers: `200 {"status":"applied"}` the first time, `200 {"status":"duplicate"}` for the same `svix-id` again (nothing changes), `400 invalid_signature` for a wrong signature or a timestamp more than five minutes off, `200 {"status":"ignored"}` for an event type outside the nine, `200 {"status":"rejected"}` for a correctly signed payload that cannot be used (it is recorded in `webhook_events` as `failed`, with a reason that holds no payload values, and acknowledged so Svix does not retry it or disable the endpoint), and `503 webhook_not_configured` when `CLERK_WEBHOOK_SECRET` is empty. Every delivery id is stored in `webhook_events`, and every change carries the Clerk object's `updated_at`, so a replayed or reordered event cannot overwrite a newer one.

**Clerk dashboard settings the API relies on.** Organizations on and **Membership required** (a session without an active organization gets 403 `no_active_workspace` from the API, and the web app sends the user to pick one). The session token must keep Clerk's default claims: the API reads `sub`, `azp`, `iss`, `exp` and the active organization (`org_id`, `org_role`, or the version 2 `o` claim). The API accepts a token only when its `azp` equals the origin of `APP_BASE_URL` exactly, so the web app has to run on that origin (`http://localhost:3000` locally).

All proxied ([D-23](05-decisions.md#d-23-product-domain-and-hostnames-contentfabriqueapp)). Names stay one level deep, because Cloudflare's free universal certificate covers the apex and one level of subdomain △. `.app` is on the browsers' HSTS preload list, so every hostname is HTTPS-only from the first request △: fine behind Cloudflare, but a plain-HTTP check fails. The API allows CORS from `APP_BASE_URL` only. |

**R2 CORS rule** (P1-01 needs it for the browser's direct part uploads; P0-09's `cfctl bootstrap` applies it to `cf-media-staging` and `cf-media-production`). The dashboard takes it under the bucket's Settings → CORS policy, `wrangler r2 bucket cors set` and the API take the same rules. `AllowedOrigins` is the `APP_BASE_URL` of that environment and nothing else (staging: `https://staging.contentfabrique.app`):

```json
[
  {
    "AllowedOrigins": ["https://staging.contentfabrique.app"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type", "content-length"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

The lifecycle rule is "abort incomplete multipart uploads after 1 day" (`AbortIncompleteMultipartUpload`, 1 day), the backstop for the API's own 24-hour clean-up. Part URLs are signed with their `Content-Length` (a part of another size is refused); the first upload on staging should confirm R2 accepts that from a browser, the way MinIO does in the tests.

**Not used, on purpose.** Cloudflare Pages (the web app is a Worker serving its own static assets), Workers KV, D1, Queues, Stream and Images. State lives in Postgres and R2 ([D-01](05-decisions.md#d-01-database-postgres-from-day-one-skip-d1-for-the-go-backend), [D-04](05-decisions.md#d-04-job-orchestration-river-on-postgres), [D-06](05-decisions.md#d-06-video-delivery-mp4-proxies-on-r2-no-cloudflare-stream-in-v1)). If a Worker later needs a cache, add the Workers KV Storage Edit permission to the bootstrap token and create a namespace with `wrangler kv namespace create <NAME>` ◐, so nothing needs preparing now.

Tokens. Apart from the tunnel token, which `cfctl bootstrap` makes, you create each one by hand in the dashboard. The bootstrap token cannot mint the others: creating tokens takes its own permission ◐, and a token that can mint tokens is far more powerful than a deploy token should be. So `cfctl bootstrap` makes the resources first, then prints which scoped tokens to create and what to pick. The permissions for each are in [§3.9](#39-scopes-and-permissions-per-token).

| Token | Variable | Created in | Lives in |
|---|---|---|---|
| **Bootstrap and deploy** | `CLOUDFLARE_API_TOKEN` | Manage account → Account API tokens → Create token (custom), before the first bootstrap ◐ | `.env` and `.env.staging` on your machine, and the CI deploy secret. Never on a server |
| **R2 S3 credentials**, a pair per bucket | `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | R2 object storage → Account Details → API Tokens → Manage → Create Account API token, once the bucket exists. The secret is shown once ◐ | the server's env file |
| **AI Gateway token** | `CF_AIG_TOKEN` | AI → AI Gateway → the gateway → Settings → Create authentication token, once the gateway exists, then switch Authenticated Gateway on. It is shown once ◐ | every environment that uses a gateway |
| **Tunnel token** | `CLOUDFLARE_TUNNEL_TOKEN` | made by `cfctl bootstrap`, no scopes | the server that runs that tunnel's `cloudflared` |
| **REST API token** (optional) | `CF_AI_API_TOKEN` | Account API tokens → Create token (custom) | only where the REST path is used |

> **Security note.** AI Gateway tokens are account-scoped: any token with the Run permission can send requests through every gateway in the account, including ones with stored provider keys ◐. So provider keys are never stored in the gateway. Our own secret store holds them and each request carries the key ([D-19](05-decisions.md#d-19-model-gateway-cloudflare-ai-gateway-in-byok-mode-openrouter-optional)). Treat `CF_AIG_TOKEN` as sensitive in every environment. If that ever matters, move production to its own Cloudflare account.

### 3.4 Postgres

> The database also needs the **`pgvector`** extension for semantic search ([D-30](05-decisions.md#d-30-semantic-search-pgvector-in-postgres-hybrid-with-full-text)); check that PlanetScale offers it, together with Postgres 18, when you create the staging database.

**Postgres 18 or newer is required**: the schema's id columns default to the native `uuidv7()` that 18 added ([D-24](05-decisions.md#d-24-public-ids-are-typeids-over-uuidv7)). The first migration refuses an older server, and `cfctl doctor` fails a Postgres URL with "Postgres 18 or newer required".

- **Local:** docker compose with the image `pgvector/pgvector:pg18` (pinned by digest, the same one as CI) and the `POSTGRES_*` values. Nothing to create, and all three database URLs point at the same local database and the same user (`cf`, a superuser), so the role split below does not apply locally. `task migrate` (or `task dev`, which runs it) creates the tables and, harmlessly, the unused group role `cf_app`. **Old data:** the volume is now `postgres18-data`, mounted at `/var/lib/postgresql` (Postgres 18 images moved their data directory), so an older Postgres 17 volume is left alone and unused. Run `task reset` to delete the old volumes, and `docker volume rm content-fabrique_postgres-data` for the Postgres 17 one.
- **Staging and production:** PlanetScale Postgres. Create one database per environment in an EU region (the research couldn't confirm EU regions, so check when you create it). △ PlanetScale must offer Postgres 18: **check when you create the database**, and pick 18 or newer. Create **two login roles** △:
  - The **app role** can `SELECT`, `INSERT`, `UPDATE` and `DELETE` on the app tables and use the sequences. It has no DDL and no superuser. Its **pooled** and **direct** connection strings go in `DATABASE_URL` and `DATABASE_DIRECT_URL`. Request traffic uses the pooled URL, and the SSE broker's `LISTEN/NOTIFY` uses the direct one, because transaction-mode poolers don't support `LISTEN`. The Go pool is set up for such a pooler (it prepares no named statements).
  - The **migrate role** owns the schema, so it can create, alter and drop. Its string goes in `DATABASE_MIGRATE_URL`, which only `cfctl migrate` reads, as a release step ([architecture §12](03-architecture.md#12-deployment-environments-observability)). **It must be a direct connection, not the pooled one:** the migrations hold an advisory lock for their whole run, which a transaction-mode pooler does not keep. It also migrates River's tables. It never reaches an app server, so a leaked server file or an injected query can't change the schema. App servers do not get this variable at all, and `cfctl doctor --env staging|production` skips it ("not on app servers") unless you set it.
- **How the app role gets its rights (P0-05).** The migrations never name your login roles. They grant the rights to a **group role named after the database: `<database>_app`** (`cf_app` for the local database `cf`), and the app login role is a member of it. Roles are cluster-wide in Postgres, so one shared group role would let the app login of one environment on a server reach the database of another; the first migration also revokes `CONNECT` on the database from everyone but the owner and this group. Every migration ends with `SELECT cf_grant_app_dml('table')` for each table it creates, a helper that grants `SELECT, INSERT, UPDATE, DELETE` (and `USAGE, SELECT` on sequences the table owns) and nothing more, so the app role cannot `TRUNCATE`, create, alter or drop. The first migration also revokes `CREATE` on schema `public` from everyone else. The one-time setup, as an administrator, in `psql`, with the real database name:

  ```sql
  -- 1. Only if the migrate role lacks CREATEROLE; otherwise the first migration creates the group role itself.
  CREATE ROLE <database>_app NOLOGIN;
  -- 2. Always: make the app login role a member. Replace the names with your database and the app role you created.
  GRANT <database>_app TO <app login role>;
  ```

  If the group role is missing and the migrate role cannot create it, `cfctl migrate up` stops in the first migration with a message that says exactly this, and changes nothing. The migrate role must own the database and its `public` schema (on Postgres 15 and later `public` belongs to the database owner): the first migration checks this up front and stops with a message if not, rather than leave DDL open to other roles. △ Whether PlanetScale's role UI offers `CREATEROLE`, group roles, membership or database ownership wasn't checked: if not, run the statements on its admin connection.
- **The job queue (River, P0-06).** The worker's River client listens on `DATABASE_DIRECT_URL` (LISTEN/NOTIFY wakes it when a job is inserted; a transaction pooler would drop that), and the api inserts jobs over the pooled `DATABASE_URL` with an insert-only client that holds no listener. The api enqueues in the same transaction as its own writes, so a job exists exactly when the write commits (the welcome job of a new workspace is the demo). `/readyz` of the worker has a `river` check: the client runs and River's tables are migrated to at least this build's version. If Postgres is down when the worker boots, the client keeps retrying and `/readyz` fails until it connects. On `SIGTERM` the worker stops fetching, lets running jobs finish for 4 s, then cancels them and waits 1 s more (cancelled jobs are retried later); River UI shuts down at the same time (2 s at most) and a start attempt still waiting on Postgres is abandoned, so the job side is done within 6 s, next to the HTTP drain (1 s) and shutdown (6 s) and the 2 s telemetry flush: 9 s inside the 10 s container grace. The worker's pool on `DATABASE_DIRECT_URL` has a fixed size of 6 (River's listener and bookkeeping only; the jobs' own queries use the pooled `DATABASE_URL`), and on staging and production the same privileged-login check as for `DATABASE_URL` applies to it (readiness check `postgres-direct`). Queues and their concurrency are `jobs.DefaultConfig` (`default` 10, `maintenance` 2). The daily `webhook_events_prune` periodic job (03:15 UTC) deletes Clerk delivery records older than 30 days, except applied membership deletes, which are the ordering tombstones of the sync and live 90 days.
- **River UI (P0-06).** `worker -river-ui-addr 127.0.0.1:8082` serves River UI on its own address, behind HTTP Basic auth: user `river`, password `RIVER_UI_PASSWORD` (compared in constant time). It is off unless the flag is given, and the worker refuses to start with the flag and an empty password, because River UI can retry and delete jobs. `task dev` turns it on at <http://localhost:8082>. In staging the worker's service definition passes the flag itself (**P0-10: add `-river-ui-addr` to the staging worker unit**) with a loopback or private address, and you reach it through an SSH tunnel or Cloudflare Access, not a public route; production leaves it off.
- **Run the migrations:** `task migrate` (up; the local `.env`), `task migrate -- status`, `task migrate -- down` (one step) or `task migrate -- down --to 0` (everything), `task migrate -- redo` (rolls back the latest migration and applies that same one again). **River's tables are part of it (P0-06):** `up` applies the goose migrations and then River's own line (`river/001_...` in `status`), and grants the group role `<database>_app` select, insert, update and delete on every `river_*` table and its sequences (only `select` on `river_migration`), so the api and worker never need DDL. A `down` that reaches 0 (`down --to 0`, or the last remaining step) removes River's tables first; `redo` and `up --to N` concern the app migrations only, and `up --to N` prints a warning that River was skipped: the api's `/readyz` has a `river-tables` check and fails until River is migrated, and creating a workspace without River's tables answers 503 `queue_not_migrated` (logged loudly, nothing written) instead of an opaque 500. `down` rolls back the app migrations first and drops River's tables only after they have reached 0, so a failing down never leaves the app schema without its queue. River versions its schema itself, so the goose files carry no River version number. For staging: `task migrate -- --env-file .env.staging up`. The same commands work without `task`: `cd apps/server && go run ./cmd/cfctl migrate …`, or a built `cfctl`. Every run prints the target as `host:port/database` with the `CF_ENV` and the env file it read, never the URL or the password.
- **`down` and `redo` drop tables and their data**, so they fail closed. They run without `--yes` only when `CF_ENV` is explicitly `local` or `ci` (an unset `CF_ENV` does not count as local), the migrate URL's host is `localhost`, `127.0.0.1`, `::1` or the compose service `postgres`, and `CF_ENV` and `DATABASE_MIGRATE_URL` come from the same place (both from the env file, or both from the environment: a staging URL exported in the shell over a local `.env` is refused). Anything else, including `bench` and `staging`, needs `--yes`; `production` is refused unless you pass `--allow-production`, and then it still needs `--yes`. Every run prints where `CF_ENV` and the URL came from. `up`, `status` and `version` are never guarded. CI sets `CF_ENV=ci` for its `db` job for this reason.
- **The app login must not be privileged.** On staging and production `cfctl doctor` reports `postgres DATABASE_URL login` (and the same for `DATABASE_DIRECT_URL`) as **invalid** when the connected login is a superuser, has `CREATEROLE` or `CREATEDB`, owns (or belongs to the owner of) schema `public` or a table in it, or can `CREATE` in `public`: the usual cause is the migrate URL pasted into `DATABASE_URL`. The api and worker enforce the same on staging and production: they refuse to start, and if Postgres is down at start they start but `/readyz` keeps failing, with an error in the log, until the check passes. Locally, in `ci` and in `bench` the app and migrate roles are one login on purpose, so doctor reports the privileges as a note on an **ok** result and the services do not check.
- **Check the split** after the first staging migration: connect with the app role's `DATABASE_URL` and run `INSERT`, `SELECT`, `UPDATE` and `DELETE` on `workspaces` (all work) and `CREATE TABLE x (id int);` (fails with `permission denied for schema public`). The test `TestRoleSplit` in `internal/store` proves the same on a local Postgres with a separate migrate and app role, on every CI run, and that one database's app role cannot connect to another database on the same server.
- **Lock down the rest of the server** (staging and production, once, as the administrator; the migrations only handle their own database). The first migration revokes `CONNECT` and `TEMPORARY` on its own database from `PUBLIC`, which closes that database to every role but the owner and the app group. Do the same for the maintenance database, which every new role can otherwise connect to: `REVOKE CONNECT ON DATABASE postgres FROM PUBLIC;`, and grant `CONNECT` to the administrator roles that need it. △ PlanetScale may manage that database itself; if the statement is refused, leave it.
- **Plans and the paywall (P0-16).** Until checkout exists (P7-01), every workspace starts with no plan, sees the paywall, and gets `402 plan_required` from the API's paid endpoints. To use the app locally, sign in once (that creates your user and workspace in Postgres), then grant yourself a plan: `task plan -- grant --user you@example.com --plan creator` (the e-mail of your Clerk account, or its Clerk user id `user_...`), and reload the page. More: `task plan -- grant ... --until 2026-12-31` (the plan runs through that whole day and ends at the start of the next one, UTC; a date in the past is accepted, so you can try an expired plan), `task plan -- revoke --user ...` (the paywall comes back) and `task plan -- show --user ...`. Plans are trial, studio, creator and pro. If the person is in several workspaces the command lists them (id, Clerk org id, quoted name, creation date, their role, member count) and asks for `--workspace wks_...` (or the Clerk `org_...` id). If an e-mail address belongs to several accounts it lists their Clerk user ids and asks for one as `--user`. A plan that the merchant of record manages (source not manual, from P7-01) is not replaced without `--force`. **Deploying:** migration 00005 drops the unused `workspaces.plan` column, so the api and the worker must be deployed together with it (an old binary that still inserts into `plan` would fail; there is no production yet). It reads `DATABASE_URL`, the app role, not the migrate role, and prints the workspace, plan, status and period end, never a URL or a secret. It follows the guard of `cfctl migrate down`: it runs without `--yes` only when `CF_ENV` is explicitly `local` or `ci`, the database is on this machine and `CF_ENV` and `DATABASE_URL` come from the same place; staging needs `--yes`; production is refused unless both `--allow-production` and `--yes` are given (for example `task plan -- grant --env-file .env.staging --user ... --plan studio --yes`; `show` never asks).
- Cost: from $5 a month per database ([D-01](05-decisions.md#d-01-database-postgres-from-day-one-skip-d1-for-the-go-backend)).

### Running it locally (P0-02)

The repository is two workspaces at the root: bun (`apps/web` as `@cf/web`, plus `packages/*`, one `bun.lock`) and Go (`go.work` with `apps/server`). Install with `task install` (`bun install --frozen-lockfile` at the root); `task dev` runs it too. Use plain `bun install` only when you change a dependency, and commit the new `bun.lock`. With Docker running:

```bash
cp .env.example .env     # first time only; `task dev` also does this if .env is missing
task dev                 # Postgres + MinIO, then web, api and worker. Ctrl-C stops the three processes
task down                # stop Postgres and MinIO (the data stays); `task reset` deletes the data too
```

| Part | Where | Comes from |
|---|---|---|
| web | `APP_BASE_URL`, http://localhost:3000 | `vite dev` (the port is fixed in `apps/web/vite.config.ts` and fails if taken) |
| api | `API_BASE_URL`, http://localhost:8080 | `/healthz`, `/readyz` |
| worker | http://localhost:8081 | `/healthz`, `/readyz` (postgres and river checks) |
| River UI | http://localhost:8082 | Basic auth: user `river`, password `RIVER_UI_PASSWORD` |
| Postgres | `localhost:5432` | `compose.yaml`, `pgvector/pgvector:pg18`, `POSTGRES_*`, volume `postgres18-data` |
| MinIO | S3 API `R2_ENDPOINT` (http://localhost:9000), console http://localhost:9001 | `compose.yaml`, volume `minio-data` |

- **`task dev` steps:** `task install`, `task env:init` (quiet when nothing changes: creates `.env` from `.env.example` if it is missing, fills the generated secrets and adds the `[AUTO]` defaults an older `.env` lacks, [§6](#6-checking-it)), `task up` (`docker compose up --wait` for Postgres and MinIO, then the one-shot `minio-init` that creates the `R2_BUCKET` bucket and is safe to run again), then `task migrate` (the database migrations, [§3.4](#34-postgres)), then `scripts/dev.sh`, which reads `.env`, builds the api and worker into `.dev/bin/` and runs the three processes. If one of them exits, the script stops the other two.
- **MinIO.** MinIO no longer publishes public images, so `compose.yaml` uses Chainguard's `cgr.dev/chainguard/minio`, pinned by the same digest as `.github/workflows/ci.yml` (change both together). Its root user and password are `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY`, and the console accepts the same pair. The bucket is created with the AWS CLI image (`amazon/aws-cli`, pinned by digest), not `mc`.
- **Local upload flow (P1-01).** The assets API needs the `R2_*` variables ([architecture §5](03-architecture.md#5-media-pipeline)); without them the api still starts and every assets endpoint answers `503 storage_not_configured`. The browser uploads parts straight to MinIO (`R2_ENDPOINT`, http://localhost:9000) with the presigned URLs the api hands out, so MinIO has to answer CORS: `compose.yaml` sets `MINIO_API_CORS_ALLOW_ORIGIN` to `APP_BASE_URL`, so the web app's origin (and no other) may `PUT` and reads the `ETag` header (MinIO exposes it by default). After changing `APP_BASE_URL`, recreate the container (`docker compose up -d minio`). The worker needs the same `R2_*` values: it removes the objects of deleted assets and runs the clean-up of expired uploads (`uploads_expire`, every 15 minutes). A worker without them logs a warning and snoozes those jobs for 5 minutes at a time without using up their attempts, so nothing is discarded for a missing setting. The 3 GB resume proof is `cd apps/server && go test -tags large -run '^TestLargeResume$' -v ./internal/auth/` (Docker; about 3 GB of disk; not part of CI): it generates the file, uploads it with 8 parallel parts from a client process, kills that process with SIGKILL part way, starts it again, and compares the SHA-256 of the stored object with the file's.
- **Local ingest (P1-04).** The worker ingests every completed upload (proxy, poster, sprite sheet, waveform, 16 kHz audio, hover preview) with ffmpeg and ffprobe **inside the `media-tools` image**, never on your machine, so build it once: `task media:build` (it runs `docker build -t media-tools:dev packages/media-tools`). **Keep it fresh:** the image holds ffmpeg and the title and caption fonts, and an image built before the fonts were added fails every render with text. `task dev` therefore checks the image on every start and rebuilds it (a cached rebuild takes seconds, the first build several minutes while ffmpeg compiles) when it is missing, when the sources it was built from differ from `packages/media-tools` as it is now (the build records the directory's git tree hash, uncommitted edits included, in the `org.contentfabrique.src-hash` label, so a rebuild that changes nothing, or a commit outside the directory, never triggers another one), or when it lacks the `org.contentfabrique.fonts=1` label; without Docker it prints a warning and the fix (`task media:build`) and carries on. `MEDIA_IMAGE_SKIP_BUILD=1 task dev` only warns. The worker also logs a warning at start when the image is missing or has no fonts label. Run `scripts/media-image.sh status` to ask without building (exit 3 means stale; `scripts/media-image.sh tree` prints the hash of the sources). The worker needs the `R2_*` variables too (it downloads the original and uploads the derivatives); without them it logs a warning and snoozes the ingest jobs. `MEDIA_SANDBOX_PROVIDER` is `docker` (the default; `hardened` is docker under gVisor and the default when `CF_ENV` is staging or production; `local` runs the host's ffmpeg with no isolation and is refused in staging and production, so use it only on a development machine that has ffmpeg 7+ with zimg), `MEDIA_TOOLS_IMAGE` names the image (never pulled at job time; the worker warns at start when Docker does not have it), `MEDIA_TEMP_DIR` is where the per-job directories and the sandbox's bind mounts live (empty: the system temp directory plus `cf-media`; on macOS it must be a path Docker shares, which the default is), and `MEDIA_CONCURRENCY` is how many ingests one worker runs at once (default 2, each up to 2 vCPUs and 3 GB). Clips up to 30 minutes are accepted. The worker removes leftover `ingest-*` directories there at start. The tests that run real ffmpeg skip when it is missing; `go test ./internal/ingest -docker-image media-tools:dev` runs them against the image, and `CF_REAL_CLIP=<file> go test ./internal/ingest -run TestRealClip -v -docker-image media-tools:dev` is the manual run on a real clip (it only reads the file and logs metadata).
- **Which value wins.** Compose lets a variable exported in your shell override `.env`, while `scripts/dev.sh` lets a non-empty `.env` value win (the same rule as `cfctl doctor`). So do not export `POSTGRES_*`, `R2_*` or the other names from `.env.example` in your shell: the services and the processes would disagree. `DATABASE_URL` and the two other database URLs repeat the `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` values, so change them together.
- Compose publishes the ports on `127.0.0.1` only, since the default credentials are `cf:cf` and `minioadmin`. A Postgres already running on your machine's port 5432 has to be stopped first, because `DATABASE_URL` in `.env.example` points there.
- `/readyz` of the api and the worker has a `postgres` check (a pool ping with `DATABASE_URL`): `{"status":"ok","checks":{"postgres":"ok"}}`, and 503 while Postgres is down. Both processes need `DATABASE_URL` to start.
- With the services up, `task doctor` reports Postgres and object storage as ok; Anthropic and Clerk stay missing until you fill the `[YOU-now]` lines.
- Other tasks: `task build`, `task test` (the database tests start Postgres in Docker and skip without it), `task lint`, `task install`, `task up`, `task migrate`, `task plan` (grant a plan by hand, [§3.4](#34-postgres)), `task gen:sql`, `task gen:api` (regenerate the Go interface and the TypeScript types from `packages/schemas/openapi.yaml`; `task gen` runs every generator), `task lint:api` (lint the spec). `task` alone lists them. `task lint` runs the same pinned `golangci-lint` as CI (through `go run`, so nothing to install) and Biome for the web app.

## 6. Checking it

**Quick check**, before `cfctl` exists. Fill in `.env`, then run:

```bash
set -a; . ./.env; set +a
for v in $(grep -E '^[A-Z][A-Z0-9_]*=.*\[YOU-now\]' .env.example | cut -d= -f1); do
  [ -n "${!v}" ] || echo "missing: $v"
done
```

It prints nothing when the three start values are present.

**`cfctl doctor --env <local|ci|bench|staging|production> [--phase P4]`** (P0-14):

- The required variables follow the tags: `[YOU-now]` and `[AUTO]` always, `[YOU-staging]` for `staging` and `production`, and the later tags once `--phase` reaches them.
- It makes one cheap authenticated call per service and never prints a value, only the variable name and ok, missing, invalid or skipped, each with a short reason such as `unreachable` or `auth rejected (HTTP 401)`. The exit code is 1 on any missing or invalid.
- **The env file.** By default `.env` for `local` and `bench`, `.env.staging` and `.env.production` for those, and none for `ci` (the process environment only). `--env-file PATH` overrides it. A non-empty value in the file wins; the process environment fills every name the file lacks or leaves empty. `--json` prints the report as JSON.
- **`CF_ENV` must equal `--env`**, because a mismatch means the wrong file was loaded. The one exception is `bench`, which runs with the local `.env` and so accepts `CF_ENV=local` too.
- **`POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB`** configure the local Docker Postgres only. They are required for `local`, `ci` and `bench`, and skipped for `staging` and `production`.
- **The AI Gateway is authenticated** ([D-19](05-decisions.md#d-19-model-gateway-cloudflare-ai-gateway-in-byok-mode-openrouter-optional)), so when `ANTHROPIC_BASE_URL` is set, `CF_AIG_TOKEN` is required in every environment. `OTEL_EXPORTER_OTLP_HEADERS` is not needed for the observability check: a local collector without authentication is valid.
- **`ci` holds no Anthropic or Clerk secrets** (CI runs in replay mode, [D-22](05-decisions.md#d-22-cheap-first-testing-ladder)). For `--env ci`, `ANTHROPIC_API_KEY`, `VITE_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` are not required, and the Anthropic, AI Gateway and Clerk checks report `skipped`. If they are set anyway, they are checked like any other environment.
- **Run it** with `task doctor` (`--env local`) or `task doctor -- --env staging --phase P4`. `task env:init` creates `.env` if it is missing, fills the three generated secrets and adds every `[AUTO]` variable from `.env.example` that has a default and is absent or empty in your `.env` (an old `.env` that predates `DATABASE_MIGRATE_URL` gets it this way). Absent lines are appended under a `# added by cfctl env init (date)` header with the example's comment, and empty ones are filled in place. It never changes a value you set and never touches a variable that is not `[AUTO]`. It prints variable names only, never values, and a second run changes nothing. `task dev` runs it on every start, silently when there is nothing to change.
- **`cfctl env lint`** (`task env:lint`, and the `env-lint` job in CI) fails when the Go or web code reads a variable that `.env.example` doesn't list. Names the platform sets (Vite's `MODE`, `DEV`, `PROD`, `SSR`, `BASE_URL`, plus `NODE_ENV` and `CI`) are on a short allowlist in `internal/envlint`.

|---|---|
| Postgres | `SELECT 1` on the three URLs (the migrate URL only when set, on staging and production), a check that the server is Postgres 18 or newer, a `LISTEN` on the direct one, and for the two app URLs a least-privilege check of the login (invalid on staging and production) |
| Object storage | put, get and delete a one-byte object with the credentials against `R2_ENDPOINT`, which proves the EU endpoint and signing |

**`cfctl bootstrap cloudflare --env <dev|staging|production>`** (P0-15) is idempotent. For `staging` and `production` it creates the EU R2 bucket with CORS and the lifecycle rule, the AI Gateway with the D-19 settings, the tunnel and the DNS records. For `dev` it creates only the `cf-dev` gateway. It then prints which values to add to `.env.<env>`, and which scoped tokens you create by hand next (the R2 credentials and the gateway token) with the permission to pick for each ([§3.9](#39-scopes-and-permissions-per-token)). It never prints the token, and running it twice changes nothing.

### CI (P0-03)

All of CI is one workflow, `.github/workflows/ci.yml`. It runs on every pull request, on every push to `main`, and by hand (`gh workflow run ci.yml`). It holds no secrets (replay mode, [D-22](05-decisions.md#d-22-cheap-first-testing-ladder)) and its token is read-only.

| Job | Runs | When |
|---|---|---|
| `changes` | decides which of the jobs below have work (`dorny/paths-filter`) | always |
| `go-lint` | `go vet ./...` and `golangci-lint` v2 with `apps/server/.golangci.yml` (errcheck, govet, staticcheck, unused, ineffassign, gosec, revive, bodyclose, errorlint, misspell) | `apps/server`, `go.work`, `.env.example` changed |
| `go-test` | `go test -race ./...` (Docker is on the runner, so testcontainers tests run) | same |
| `db` | `cfctl migrate` up, down to 0, up and redo against a Postgres 18 service, and a check that the committed sqlc output (`internal/store/db`) is current | same |
| `web` | `bun install --frozen-lockfile`, then `@cf/web` typecheck, lint (Biome, `apps/web/biome.jsonc`), test, build, and a check that `routeTree.gen.ts` is up to date | `apps/web`, `packages`, `package.json`, `bun.lock` changed |
| `env-lint` | `cfctl env lint` (scans the Go and web code) | `apps`, `packages`, `.env.example` changed |
| `doctor` | `cfctl doctor --env ci` against Postgres and MinIO | `apps/server`, `.env.example`, `compose.yaml` changed |
| `required` | passes when every job above succeeded or was skipped, fails on any failure or cancellation | always |

- **Mark only `required` as a required check on `main`.** A required job that a path filter skips stays "pending" and blocks the pull request for good. `required` always runs, so a docs-only pull request skips the rest and still goes green. A new job must be added to `required`'s `needs:` list, or its failure won't block merging.
- **On `main` and manual runs every job runs.** Path filtering applies to pull requests only.
- **Speed.** The jobs run in parallel, Go modules and the `-race` build cache are cached on `go.sum` (only `go-test` saves it, `golangci-lint` has its own cache) and bun's download cache on `bun.lock`. A newer push to the same pull request cancels the older run; runs on `main` are never cancelled. The target is under 10 minutes on a cold cache.
- **Actions and images are pinned by digest**, with the version in a trailing comment (`pgvector/pgvector:pg18` and MinIO are pinned the same way in `compose.yaml` and `ci.yml`, and the Postgres digest also in the `doctor` and `db` jobs and `internal/store/storetest`: change them all together). Renovate keeps them current. The `golangci-lint` version is pinned in `ci.yml`; use the same major locally.
- **Renovate** (`renovate.json`): runs Monday before 06:00 Europe/Amsterdam, opens one pull request per ecosystem for minor and patch updates (Go modules, bun packages, GitHub Actions, Docker images), and separate pull requests for the Go toolchain (`go` directive), the bun version (`packageManager`) and `golangci-lint`. It runs `go mod tidy` after Go updates, never automerges, and keeps a Dependency Dashboard issue. Install the app first ([§3.5](#35-servers-ci-and-github)).
