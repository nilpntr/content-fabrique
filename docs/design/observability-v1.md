# Design note: following the agents step by step (observability v1)

> Status: **proposed** · 2026-10-18 · Applies [D-39](../05-decisions.md#d-39-local-traces-and-evals-in-arize-phoenix). Extends [architecture §7 and §12](../03-architecture.md) and the runtime of [agent-runtime-v1](agent-runtime-v1.md). The founder's request: "an MLflow-like tool in the local Docker stack, so you can follow each step and check what is going wrong, because the output is only as good as the input; and a self-improvement loop to tweak."

## 1. What it is

Three parts, each its own PR:

1. **Traces (this note, sections 2 to 6).** Every agent run is a trace: the run, its context, every model call with what was sent and what came back, every tool call with its arguments and result, the checks of `check_edit`, the budget notes, and the renders the run asked for. Locally they go to Arize Phoenix in the compose stack. Stored runs from before can be replayed into it (`cfctl trace export`).
2. **Eval suite and judge** (section 7, with PR 2).
3. **The improvement loop** (section 8, with PR 3): `cfctl eval improve`.

## 2. Phoenix in the local stack

- `compose.yaml` has a `phoenix` service under the profile `obs`, so `task up` and `task dev` never start it. The image is `arizephoenix/phoenix:version-20.23.0-nonroot`, pinned by digest. One port, `127.0.0.1:6006`, serves the UI and the OTLP/HTTP ingest (`/v1/traces`); gRPC is not used. Its SQLite database lives in the `phoenix-data` volume, mounted at the image user's home (uid 65532), the one directory it may write. Phoenix's own usage telemetry is off (`PHOENIX_TELEMETRY_ENABLED=false`).
- **`task dev:obs`** is `task dev` plus `task obs:up` (`docker compose --profile obs up -d --wait phoenix`), and `scripts/dev.sh` then exports, for its own three processes only, `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:6006`, `OTEL_TRACE_CONTENT=1` and empty `OTEL_EXPORTER_OTLP_HEADERS`. These win over `.env`, so a hosted endpoint written there never receives content from `dev:obs`; the script refuses to run with any `CF_ENV` but `local`. `task obs:down` stops Phoenix and keeps its data.
- **cfctl** sends spans when `OTEL_EXPORTER_OTLP_ENDPOINT` is set in the env file or the environment (it passes the endpoint and headers to the exporter itself, since its settings come from the env file). `cfctl agent run` prints the Phoenix link of the run's trace at the end.
- **Licence.** Phoenix is under the Elastic License 2.0: we may run it for our own development; we may not offer it, or a product built around it, as a hosted service. It never ships to staging or production and is not part of the product.
- **Considered:** MLflow (its tracing UI is younger and centred on its experiment tracker; more weight than we need for a trace viewer), Langfuse (MIT core and a good UI, but the self-hosted stack is Postgres, ClickHouse, Redis and blob storage: four more containers on a laptop). Phoenix is one container, reads OpenTelemetry with the OpenInference conventions directly (no SDK of theirs in Go), shows images inside LLM messages, and has datasets and experiments with a REST API for part 2.

## 3. What a span may carry

- **Metadata, always** (when an endpoint is set): ids, the agent, stage, routing profile, model, effort, budgets, token counts, costs, reservations, `max_tokens` as sent, stop reasons, tool names, whether a tool failed, artifact ids, check ids with pass or fail, durations, failure reasons.
- **Content, only with `OTEL_TRACE_CONTENT=1` and `CF_ENV=local`** (`telemetry.ContentAllowed`, the one rule): the system prompt, the conversation, the run's input and output, tool arguments and results, thinking summaries, check details, the run context, and thumbnails of the frames the model saw. `config.Load` refuses to start staging or production with the variable set to 1, `cfctl doctor` reports it invalid outside local, and ci and bench ignore it. Staging and production keep exporting to Axiom, with metadata only: those spans are new there, and they carry no prompt, no creator text and no picture.
- **Secrets never.** Every text a span carries goes through `telemetry.Redact` first: the query string of a presigned URL (anything with an `X-Amz-*` signature or credential, `signature=`, `token=`, `key=`, `expires=`) becomes `?[redacted]`, bearer tokens and the shapes of our keys (`sk-ant-`, `sk_`/`rk_` test and live, `whsec_`) are removed. Keys never reach the agent layer to begin with (D-18): the factory is the only code that reads them, and the spans are built above it.
- **Sizes.** One message part is at most 16 KB of text, a JSON value 32 KB, a thumbnail 8 KB (144 px on the long side, at most 32 per call, only for the images the call is the first to send; older ones are named by their storage key). A model call's messages are held to 384 KB: the system prompt and the run context stay, the newest messages fill the rest, and a note says how many in between were left out (each one is in the span of the call that first sent it). The tracer provider allows 4096 attributes a span (the SDK's default of 128 would cut the flattened messages), and with content on the exporter sends batches of 16 spans.

## 4. The tree

All spans of a run share one trace whose id is the run's UUID (`telemetry.RunTraceID`, through the provider's `telemetry.IDGenerator`): a run found in the database is found in Phoenix by its id, a second claim of the run (a resume, the answer to `ask_user`) adds a second root span to the same trace, and the renders the run asks for join it. Phoenix groups the runs of a project as one session (`session.id` is the project id).

| Span | Kind | From | Carries |
|---|---|---|---|
| `agent.run <agent>` | AGENT | `runtime.Runner.Execute`, one per claim | `cf.run_id`, workspace, project, agent, stage, `cf.routing_profile`, model, effort, budgets (`cf.budget.*`), epoch, resumes; the editor adds `cf.prompt_version`, `cf.vibe`, and after `plan_edit` `cf.playbook`, `cf.content_type`, `cf.target_length_s`, `cf.tempo_bpm`, `cf.pace`. At the end: `cf.status`, `cf.failure_reason`, `cf.cost_micros`, token totals, tool calls, active time. Content: the run's input and output. Events: `claimed`, `cost_reconciled`, `cut_off`, `nudge`, `waiting_input`, `budget.limit_reached` (limit, graceful) |
| `agent.context` | CHAIN | the run context, once per run | content: its text |
| `llm.<stage>` | LLM | `llm.metered`, every model call of every stage (the editor, the quick look, the style read, the judge) | `llm.model_name`, `llm.invocation_parameters` (max_tokens as sent, effort, thinking, tool choice), `cf.max_tokens_asked`, `cf.shortened`, `cf.reserved_micros` (the worst case held against the caps) and `cf.reserved_budget_micros`, `llm.token_count.*` (prompt, completion, cache read and write), `cf.cost_micros` and `llm.cost.total`, `cf.price_table_version`, `cf.estimated`, `cf.stop_reason`, `cf.request_id`, the tools offered and called; a refusal by a cap is an event `spend_cap_refused` naming the cap. Content: `llm.input_messages` and `llm.output_messages`, `cf.thinking` |
| `tool <name>` | TOOL | the loop, every tool call | `tool.name`, `cf.tool_use_id`, `cf.mutates`, `cf.resumed`, `cf.is_error`. Content: `tool.parameters`, the result as `output.value`. Events: `artifact` (kind, version, duration, ids), and for `check_edit` one `check` event per check (`cf.check.id`, `cf.check.status`; the detail with content), a summary `check_edit` event and `style_distance` (every check of the report, so the text, caption, face, overlay and music checks are events too); `title_recipe` when edit_timeline gave title graphics the creator's title look; `budget.low` when the tool told the model it is running out; `preview` with the contact sheet's key |
| `render <profile>` | CHAIN | `renderjobs.Pipeline.Run` in the worker | render id, project, version, profile, who asked, `cf.duration_ms`, `cf.wall_ms`, `cf.ffmpeg_ms` (the sandbox time), `cf.cpu_ms`, size, status and failure reason; children `render.ffmpeg` and `render.contact_sheet`. A render an agent run asked for is in the run's trace |

## 5. Replaying a stored run

`cfctl trace export --run <run_...> --workspace <wks_... or org_...>` (development only) reads the run row, its events and its `usage_ledger` rows and sends the same tree to Phoenix (or `--endpoint`), at the times the events were written. Nothing runs again and no model is called. It rebuilds the conversation as the loop does (`runtime.ExportTrace`), so each model call shows the messages it was sent; it matches each answer to its ledger row by request id (price table version, estimated or not); a ledger row with no stored answer is a span of its own; a tool call with no result is marked; the `edit_check` artifacts give the check events. The system prompt is shown when the run used the prompt version this build has; an older run's spans say which version it used instead. With object storage configured it reads the frames each call sent first and shows them as thumbnails (`--thumbnails`, default 40 calls). Content is on by default when the endpoint is on this machine (`--content=false` turns it off). The trace id is derived from the run's id (`replay/<run>`), and each span's id from the event, so exporting twice sends the same spans.

## 6. Tests

No paid calls: the LLM span is tested over the llm package's fake API (metadata only without content, no key or brief text in any attribute; messages, thumbnails and redaction with content; a cap refusal); the runtime's spans over the scripted model and Postgres (one trace per run with the run's id, tool spans under it, content only when on); the replay over a stored run (the same tree, derived and stable ids, times in order); `telemetry` (redaction, the content rule, ids, thumbnails, the message budget); `config` and `cfctl doctor` (the variable is local-only).

## 7. The eval suite and the judge

`cfctl eval suite [--suite suites/back-day.yaml] [--live --max-usd N]` (package `internal/evals`) scores a set of cases.

- **A suite file** (`suites/<name>.yaml`, checked in, placeholder ids) lists cases: a workspace, footage asset ids, a song, a brief, a vibe, a routing profile, a budget, `expectations` (rubric items with weights), and `stored: {project, version}` for a version that exists. The real ids live in `suites/<name>.local.yaml` (gitignored, same shape, merged by case id). Creator footage, references and renders are never committed. A case can be `held_out` (never shown to the improvement loop) or a `calibration` case (a version with a recorded human verdict and the range each judge dimension should fall in; it does not count in the mean).
- **A case runs** on its stored version (free: the checks are Go), or with `--live` the editor first edits a new project made from its footage, song and brief, in-process, with no credits and the case's budget (a worker must be running for the previews). `--max-usd` is the hard total for editor runs and judge calls together: an editor run is started with its budget less the judge's reserve and only when at least $0.30 is left, a judge call only with $0.03 left. With `--max-usd 0` (the default) nothing is spent and the judge answers only from its cache.
- **Deterministic scores:** every `check_edit` check (`editor.CheckVersion`, as check_edit and `cfctl eval editor` run it, with the preview render measured), the style distance, the music sync (from the measured beat data: the share of cuts on a beat, as 1 to 5), and the **recorded human feedback** (`suites/feedback.yaml`): each item has a weight (3 by default) and, when measurable, a detector (`transitions_ai`; `text_on_body`, which reads the body, face and overlay placement checks, since D-38 lets a caption creator's story lines sit over the chest but never the face; `static_long_takes`; `music_only`) that scores it from the timeline and the checks. The seed items are the founder's: effect transitions read as AI, text must not cover the body, static long takes feel dead, music only.
- **The AI judge** (`judge_edit`, prompt `judge_edit.v2`): one strict, forced tool call per case with the render's contact sheet, strips of the frames 200 ms before and after up to 12 cuts (cut from the preview mp4 in the media sandbox), contact sheets of up to three of the creator's reference videos (a local directory, `references_dir`; the ones the style profile names first), the style profile, the brief, the plan and the timeline as untrusted data (every clip and transition, and every text item and graphic: the title, story captions, chapter cards and the other templates, with their words, time, place and placement rule), the rubric and the human feedback. It scores 1 to 5, rationale first, on hook, energy and pace, "looks like an automatic AI edit" (inverted in the score), text legibility and placement, style match and story arc, and each rubric item. Music sync is given as a measured fact, not judged. **Model: Sonnet 5.5**, resolved from `v1-start` whatever `ROUTING_PROFILE` says (`--judge-profile` overrides), so scores are comparable between runs: about 12,000 input tokens and at most 3,000 out is about $0.05 worst case, inside the **hard $0.10 budget per case** (a `llm.RunBudget`, so a call that cannot fit is cut or refused before it is sent); Opus 5.5 costs twice as much and its worst case with the pictures would not fit. `dev-cheap` keeps a Haiku entry so the profile stays Haiku-only. Verdicts are cached by the hash of every input (`eval-results/.judge-cache`): a check-only change judges the same render again for free.
- **The score** of a case is a weighted mean from 0 to 100: checks (weight 2, the share that pass), style (1), each judge dimension (1), music sync (1), each rubric item (its weight), each measured feedback item (its weight, 3: one feedback item outweighs any three judge dimensions). The suite's mean leaves out calibration and held-out cases; the held-out mean is reported apart.
- **Results** go to `eval-results/<suite>/<run>.jsonl` (gitignored; one line per case and a summary) and, when Phoenix answers, to Phoenix: the suite is the dataset `suite-<name>` (one example per case, updated in place by case id), the run is an experiment, each case a run linked to its trace (`eval.case <id>`, with the judge's LLM span under it), each score an evaluation (CODE for checks, style and music sync, LLM for the judge with its rationale, HUMAN for the feedback and the calibration).
- **Calibration:** `calibration-founder-v4` is v4 of the founder's "sick, except its transitions" project: the judge should give a high hook and energy and an ai_look of 3 or more (the transitions), and the feedback detector fails it for its punch and zoom transitions.

Tests: suite loading and merging (the checked-in file has only placeholders), the detectors, the weights (a failed feedback item costs more than a perfect judge gives), music sync and calibration, the judge over a fake model (its request, the strict tool, untrusted data, the $0.10 budget, the cache, bad answers refused), Phoenix over a fake server, and a whole run over fakes (nothing spent without a budget, the edit and judge budgets inside `--max-usd`, placeholders skipped, the JSONL and the experiment written).

## 8. The improvement loop

`cfctl eval improve --max-usd N [--iterations N] [--live]` (`internal/evals/improve.go`, `improver.go`) tweaks the editor one change at a time and keeps only what the suite says helped.

1. **Baseline:** the suite on the current code (in-process, label `baseline`, with up to half of `--max-usd`).
2. **Low cases:** the lowest-scoring cases (`--low`, default 2; never held-out or calibration cases) with their failing checks, the judge's scores and rationales, the failed human feedback and the music sync.
3. **The improver** (`improve_edit`, prompt `improve_edit.v4`; Opus 5.5, resolved from `v1-start` whatever `ROUTING_PROFILE` says; at most `--improver-usd` a call, default $0.50, inside `--max-usd`): it is shown the allowlist's files (the editor prompt and the playbooks whole; `check.go`, `pace.go`, `checktext.go`, `check_graphics.go`, `checkmusic.go` (the text, caption, face, overlay and music checks), `render/profile.go` and `styleprofile/thresholds.go` as their top-level const and var blocks only), the recorded feedback and what was already tried, and proposes **one change**: 1 to 4 exact replacements in one file (strict forced tool). The allowlist is code (`evals.AllowedFiles`): prompt, playbook, check threshold, renderer default, style rule; anything else is refused, and so is an `old` text that does not occur exactly once. `--proposal file.json` tries a change of your own instead, with no model call.
   - **A refused proposal is asked again, not wasted** (the first live run's improver answered with "x" for the title and the path, and the round ended). Before any edit is applied the proposal is checked: a title of 2 to 20 words that is not a placeholder, a rationale, an expected effect, 1 to 4 edits in one file of the allowlist, each old text found exactly once. A refused proposal goes back to the improver in the same conversation as a tool result with the exact error, and it is asked again, up to 3 proposals within the iteration's improver budget (the file blocks carry a cache breakpoint, so a retry reads them from the prompt cache); after the third the iteration fails with the last error. Every attempt and its error is in the report and is an event of the iteration's span. The tool schema now restricts `path` to an enum of the files shown (strict tool use takes enum, not lengths or patterns), and has a `no_change_reason` field: an improver that finds nothing worth changing says so (the iteration ends as "not evaluated") instead of sending a stub. The files are shown as `<file path=...>` blocks of our own source, not as untrusted data, with a note that the editor prompt among them addresses another model.
   - **What the "x" call was.** The span of that call (`llm.improve_edit`, request `req_011Cg9agr9mZheVPTkQrowJB`) shows one model call, no reminder retry, stop reason `tool_use`, 730 output tokens of which most were Opus's adaptive thinking (Opus 5.5 cannot turn it off), so the tool call itself was a short stub. Content capture was off for that cfctl run, so the text cannot be recovered; what the evidence rules out is the reminder path of `llm.CallTool` (it did not run) and a cut-off answer. The schema let it through because every field was a free string: strict tool use guarantees the shape, not the sense. The enum, the text check and the retry now cover it; run the loop with `OTEL_TRACE_CONTENT=1` to see the messages next time.
4. **Apply and measure:** a scratch worktree under `.eval-worktrees/` (gitignored) on a new branch `improve/<suite>-<time>` from HEAD; the change is applied, built (`go build`, `go vet` of the touched packages) and committed, and the suite runs on that code (`go run ./cmd/cfctl eval suite` in the worktree, with the same suite, local file, env file and results directory, so the judge's cache is shared and an unchanged render is not judged again). A check-threshold, renderer or style change is measured on the stored versions; a prompt or playbook change changes only what the model is told, so it needs `--live` (the baseline is then live too); without it the change is reported as not evaluated.
5. **Keep or drop:** kept only when the noise-aware rule of section 9 holds (a paired, case-by-case gain of at least `--min-gain` and more than twice its standard error; no case dropping beyond `--max-regression` or its noise; the held-out mean holding; the failure rate not rising); otherwise the commit is dropped from the scratch branch. With `--iterations` above 1 the next change builds on the last kept one.
6. **Report:** `eval-results/improve/<branch>.md`: per iteration the change, its rationale, the decision and its reasons, before and after per case with the trace links of both runs, the Phoenix experiments and the diff. The worktree is removed; the branch stays only when something was kept. **It never pushes**: the director reviews the branch and opens the PR.

Every iteration is a span (`eval.improve.iteration`) under the loop's `eval.improve` span, with the change, the means before and after, the decision and the diff; each suite run is an experiment (`baseline`, `candidate N: <title>`). Spend: nothing beyond `--max-usd` (the improver calls, the judge calls and any live editor runs together). Tests: the rule, the allowlist and the excerpts, validation and application, the loop over fakes (kept, rejected, refused, not built, not evaluated without `--live`; the improver never sees a held-out case), the git side over a temporary repository, and the improver's request and answer over a fake model.

## 9. Telling signal from noise

The first live `cfctl eval improve --live --max-usd 10 --iterations 2` ($5.59) showed the loop could not tell a change from chance: the same code on the same case scored 91.0 (stored), 85.0 and 83.7 (live), the held-out case 89.3, 84.2 and 90.1, against a `--min-gain` of 0.5. The loop is now built on that spread (`internal/evals/stats.go`, `baseline.go`).

- **Samples.** A live case runs `--repeat` times (default 2 with `--live`, at most 10); a stored case once, because its checks are computed in Go and its judge verdict comes from the cache, so it scores the same every time. A case's score is the mean of its samples with their standard deviation; the run's mean comes with its standard error. Both are in the terminal (`mean ± sd (n)`), every JSONL line (`samples`, `sd`, `n`, `failures`, `failure_rate`; the summary has `mean_se`, `held_out_se`, `failure_rate`, `calibration_error`, `code_hash`) and Phoenix (an experiment with `repetitions`, one run per sample with its own trace and `sample_score`, the case's mean and details on its last sample).
- **Failures score 0.** A live sample whose editor run did not succeed (its budget, an answer cut off at `max_tokens`, any error, or no version) is a bad outcome of the code, not a missing measurement: it counts 0 in the case's mean and is listed (`FAILED sample 2: the editor run run_... failed: budget`). The failure rate (failed samples over samples) is its own metric. A sample the judge could not score (its parts would be missing) is left out of the mean when another sample of the case was judged.
- **The rule** (`evals.Accept`), paired by case: each case is its own control, so the spread between cases is not noise. The gain is the mean over the comparable cases of mean_after − mean_before; its standard error is √(Σ var_before/n_before + var_after/n_after) / cases, with a case's own variance when it has two or more samples, `--noise-sd` (default 4, from the runs above) for a live case scored once, and 0 for a stored case. A change is kept only when (a) the gain is at least `--min-gain` and more than twice its standard error (about a one-sided 95 % test; with two or three samples the sd is rough, which the factor absorbs better than a t-table would pretend to); (b) no case drops by more than `--max-regression` or twice its own noise, whichever is larger (a drop inside the noise is not evidence of harm); (c) the held-out mean drops by no more than `--held-out-slack` or twice its noise; (d) the failure rate does not rise. Every line of the decision, with its numbers, is printed and goes in the report. A bootstrap was considered: with two or three samples a case it resamples the same few numbers and claims a precision it does not have.
- **The infrastructure stops a run; it is never scored** (`internal/evals/infra.go`). A live candidate once hit the workspace's $20 daily spend cap after its first case: every later sample failed with `daily_cap`, scored 0, and the candidate was rejected for a 73 % failure rate it had nothing to do with. An editor run's failure reason now decides whose fault it was. The infrastructure's (`daily_cap`, `platform_spend_paused`, `spend_cap_busy`, `request_cap`, `model_access`, `model_error` (overloaded, 429, 529), `model_outcome_unknown`, `replay_miss`, `ledger_error`, `context_failed`, `internal_error`, `too_many_resumes`, `corrupt_log`, `unknown_agent`; a run that could not be started or worked, i.e. no worker; a measurement that could not read the render or the database) stops the run at that case: the case is not scored, the run says `stopped at case <id>: <what happened>; nothing was decided` with what was spent, `cfctl eval suite` exits 3, and the run is never cached as a baseline. In `cfctl eval improve` a stopped baseline ends the loop and a stopped candidate ends the round (the candidate is dropped, not rejected); the report says **Stopped by the infrastructure, nothing was decided** and what was spent. The edit's own failures (its budget, `max_tokens`, `refusal`, `context_window_exceeded`, `event_too_large`, `unexpected_stop_reason`, an editor error, no version) still score 0.
- **Room before a live run.** Before a live `cfctl eval suite` or `eval improve` starts, the estimate is checked against what today's caps leave: each live workspace's daily cap less its spend today, and, when the calls are billed to the platform, the platform breaker (refused when it is open). A run the caps cannot cover is refused up front (`not started: the workspace's daily spend cap ($20.00) has $3.10 left today, less than the estimated $6.40 ...`, exit 3) rather than stopped half way.
- **Like against like.** A candidate runs live when the baseline did, whatever kind of change it is (before, a check-threshold change was compared on stored versions against a live baseline).
- **Baseline cache.** A run is remembered (`eval-results/<suite>/baselines.json`) by a hash of the code that decides a score (the editor package with its prompts, playbooks, tools and checks; the renderer; the timeline rules; the style profile; the scoring itself; `config/routing`; the format library, `internal/formats` and `config/formats`; and `cfctl`'s `eval_suite.go`, which makes the live cases), the suite, its local and feedback files, and the run's options (live, repeat, judge, judge profile, cases). `cfctl eval improve` reuses a complete run of the same hash younger than `--baseline-max-age` (24 h) instead of running a baseline, and says so; a run cut short by the budget, or whose judge calls were skipped for it, is never remembered. `cfctl eval suite` records its runs too, so a suite run just before the loop is its baseline.
- **Cost guard.** Before anything is spent both commands print an estimate and refuse to start when it is over `--max-usd`: per case, samples × (the case's mean editor cost in the last ten runs, or its budget when it has none, plus the mean judge cost, or $0.10), and for the loop the baseline (unless cached) plus, per iteration, the improver's budget and a candidate run. It leans high: a stored case's verdict often comes from the cache for nothing.
- **Judge calibration: anchors.** The judge gave the founder-approved v4 a 3 for hook and energy where the founder says 4 to 5. Each judge call now starts with the calibration cases as anchors: their render's contact sheet, what the human said and their ranges ("hook 4-5, energy_pace 4-5"), with the instruction that an edit as good as the anchor on a dimension scores at least the bottom of its range. A calibration case is never shown its own anchor, so its agreement stays a real test, and the run reports the calibration error (the mean distance of the judge's scores from the human ranges; 0 agrees). Anchoring was chosen over z-normalising the judge's dimensions: z-scores need many judged edits per dimension before they are stable, and they would move every score when a case is added; an anchor is one picture (about $0.003 a call), works from the first run, and its effect is visible in the calibration error. The prompt is `judge_edit.v4`, so earlier cached verdicts are not reused; `judge_edit.v5` adds the format the plan chose and how to score concept and novelty items ([formats v1](formats-v1.md)).
