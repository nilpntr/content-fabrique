# Design note: model access, agent runtime and the first editor slice (P4-00, P4-01, P4-02)

> Status: **accepted for P4** · 2026-10-17 · Applies [D-07](../05-decisions.md#d-07-agent-runtime-go-native-loop-on-the-claude-messages-api), [D-17](../05-decisions.md#d-17-model-routing-is-data-tuned-by-benchmark), [D-18](../05-decisions.md#d-18-who-pays-for-tokens-managed-credits-or-bring-your-own-key), [D-19](../05-decisions.md#d-19-model-gateway-cloudflare-ai-gateway-in-byok-mode-openrouter-optional), [D-21](../05-decisions.md#d-21-testing-on-the-first-party-api-self-funded) and [D-22](../05-decisions.md#d-22-cheap-first-testing-ladder). Extends [architecture §7 and §11a](../03-architecture.md#7-agents). Each P4 task is briefed from this note, and any task that breaks a rule here changes the note in the same PR.

## 1. Order

**P4-00 is split in two:**
- **P4-00a, managed access** (local, ci and bench need it now): the client, the factory with the platform key, the ledger, the price table, the rate limiter, record and replay, and spend caps.
- **P4-00b, the BYOK vault**: key custody, the settings UI and the gateway conformance test.

The gateway itself needs P0-09, which is the founder's Cloudflare work. Until it exists, `ANTHROPIC_BASE_URL` is empty and calls go direct (D-19 bypass).

**The rest:** P4-00a → P4-01 runtime → P4-02 editor tools, the first slice (§5) → P4-03 prompt. P3-04, P3-05 and P3-06 (the renderer's text, audio and render jobs) run in parallel.

## 2. Model access (P4-00a)

`internal/agents/llm`:

- **`Client` interface.**
  - Calls: `Messages(ctx, Request) (Response, error)` and `CountTokens`.
  - `Request` holds the model ID, system blocks, messages, tools, `max_tokens`, `thinking`/effort and `cache_control` marks.
  - `Response` holds the content blocks, the stop reason and `Usage` (input, cache write, cache read and output tokens).
  - The Anthropic implementation uses `anthropic-sdk-go`. The base URL is `ANTHROPIC_BASE_URL`, or api.anthropic.com when that is empty. With the gateway, each request also carries `cf-aig-metadata` (workspace, run, stage and profile) and `cf-aig-collect-log-payload: false`.
- **`ClientFactory.For(ctx, workspace, stage)`** returns a client plus a `Billing` label. In P4-00a every workspace is **managed**, using `ANTHROPIC_API_KEY`.
  - `billed_to` is `test` when `CF_ENV` is local, ci or bench, and `platform` in staging and production.
  - The factory is the only code that reads a key. Agents and tools never see one.
- **Routing:**
  - `llm.Router` resolves `(profile, stage) → {model, effort, max_tokens}` from `config/routing/*.yaml`. These files already exist from P0-14; `ROUTING_PROFILE` picks the profile.
  - The editor stage runs Opus 5.5 in `v1-start`, and Haiku 5.5 in `dev-cheap` (D-22 ladder).
  - A run may override the profile, so a test can use `v1-start` explicitly while the environment default stays `dev-cheap`.
- **Price table:**
  - `config/pricing/2026-10.yaml` holds, per model, the price per million tokens for input, cache write (5 minute and 1 hour), cache read and output, with a `version`.
  - Every call writes one `usage_ledger` row: workspace, run, stage, model, the four token counts, `list_cost_micros`, `price_table_version`, `billed_to` and the `request_id`.
- **Spend caps,** all enforced before the request is sent:
  - per-run `budget_micros`, by reservation: a call reserves its worst case before sending and settles with the actual cost, so concurrent calls of one run cannot overspend;
  - per workspace, `DAILY_SPEND_CAP_MICROS` (a new variable, default $20 locally);
  - a process-wide `LLM_MAX_REQUEST_MICROS`, which estimates a request's cost from its counted tokens and refuses anything absurd.
- **Rate limiting:** a per-key semaphore (default 4 concurrent requests). On 429, 529 and the 5xx answers the client backs off exponentially with jitter and honours `retry-after`. Retries live only here (details under "As built").
- **Record and replay** (`LLM_MODE`):
  - **The key:** a SHA-256 over the canonical request. That is the model, system blocks, messages and tools, as canonical JSON with images replaced by the SHA-256 of their bytes, plus the parameters.
  - **`record`:** calls the API and writes `testdata/cassettes/<stage>/<key>.json`, holding the redacted request summary, the response and the usage. The key and headers are never written.
  - **`replay`:** serves from cassettes. A miss is an error that names the key and the stage, never a silent call to the API.
  - CI always runs `replay`.
- **As built in P4-00a** (details the sections above leave open):
  - **Layers**, outside in: `metered` (resolves image references, reserves against the caps, writes the ledger row), `cassette` (record or replay), `limited` (per-key lanes, retries), `anthropic` (the SDK, `MaxRetries` 0). The runtime calls only `llm.Client`.
  - **Caps work by reservation.** Before sending, a call works out its worst-case cost: input tokens at the dearest rate they could be billed (a cache write when the request has breakpoints; Haiku 5.5's long-prompt tier whenever input plus `max_tokens` could cross 100,000), plus `max_tokens` at the output price. The input tokens are exact for any request with an image (an image costs thousands of tokens depending on its size, so such a request is always counted); for text only they are a cheap local upper bound (canonical bytes / 2 plus 2,000 for overhead), and the call asks the free `count_tokens` only when that bound does not clear `LLM_MAX_REQUEST_MICROS`, or the run budget or daily cap cannot cover the inflated bound. The call is refused when the worst case is over `LLM_MAX_REQUEST_MICROS`, over the run's budget, or over what is left of `DAILY_SPEND_CAP_MICROS` today (UTC).
  - **Run budget** is `llm.Budget { Reserve(micros) (release func(actual int64), error) }` (`llm.RunBudget` is the in-memory implementation; the runtime backs it with `agent_runs.budget_micros`). A call reserves its worst case, then settles with the actual cost: the usage's cost on success, 0 on a definite failure, and the reserved amount when the outcome is unknown. Concurrent calls of one run therefore can never overspend, and the runtime's own checks (section 3, step 1) read `Remaining()`/`Spent()` of the same object.
  - **Daily cap** reserves in process first, remembers the total reserved at that moment, reads the ledger, then checks `spent + reserved_before + estimate <= cap`, and releases on failure. The reservation is released only after the call's ledger row is written, so a concurrent call sees an earlier call as a reservation or as a row, never as neither. Calls of other processes are not seen; the overshoot is bounded by their concurrency times the per-request cap. A cap that cannot be checked (the ledger is unreadable) refuses the call.
  - **A call that was sent and got no usage back** (a timeout, a reset, a body cut off: `llm.ErrOutcomeUnknown`) may have run and been billed. It is written to the ledger as an `estimated` row at its reserved worst-case cost, and charged to the run budget the same way, so caps stay conservative. It is never retried by the client, and the runtime must not retry it blindly: it should read the run's events and the ledger first. A transport failure before the request reached the wire is safe and is retried.
  - **Timeouts** follow the model: two minutes plus three times the time `max_tokens` takes at a slow-case speed (Opus 20, Sonnet 40, Haiku 80 tokens/s), between 10 and 60 minutes. Opus 5.5 with `max_tokens` 16000 gets 42 minutes. Streaming is not used yet.
  - **Retries** (the same exponential backoff with jitter, `retry-after` honoured, bounded attempts and total wait): error answers 408, 429, 500, 502, 503, 504 and 529 (the server did not take the request, so a retry cannot bill twice), and transport failures of a request that never reached the wire (any transport failure for `count_tokens`, which is free and idempotent). Every other 4xx is never retried.
  - **Lanes:** each API key has a Messages lane and a `count_tokens` lane, each with its own slots (`LLM_KEY_CONCURRENCY`) and its own cool-down after a 429 or 529, so a long generation or a throttled Messages call never stalls the free count.
  - **Ledger** has two extra columns: `cache_write_1h_tokens` (the part of `cache_write_tokens` written with the one-hour lifetime, because the two lifetimes are priced differently) and `estimated` (see above). `request_id` is unique when present. When a response reports cache writes without their split by lifetime, they are priced at the 1-hour rate if the request asked for a 1-hour breakpoint. A call that returns usage and then fails is still written. If the row cannot be written after retries, the paid response is returned together with `llm.ErrLedger`, and the row is logged for reconciliation. The ledger's foreign key to `workspaces` is `RESTRICT`: billing history is not deleted with a workspace (workspaces are soft-deleted today), and a future purge has to move or anonymise the rows deliberately.
  - **Prices** are integers (micro-dollars per MTok) and costs round up. A model with a `null` price is refused unless `LLM_ALLOW_UNPRICED=1` (local and ci only; staging and production never run an unpriced model, D-31). Haiku 5.5 has a long-prompt tier (over 100,000 prompt tokens), modelled in the table.
  - **Routing:** a stage marked `enabled: false` (or under such a group) does not resolve (`llm.ErrStageDisabled`), and `cfctl doctor` leaves its model out; a test keeps the two sets equal.
  - **The `quicklook` stage (P1-04b)** is in every profile, mapped to `claude-haiku-5-5` with `max_tokens` 400: no profile routes it higher, because each call has a $0.003 budget (`llm.RunBudget`, reserved before sending) and costs about $0.0003. It is the first model call outside an agent run, so its ledger rows carry the **asset's id as `run_id`** (one query gives a clip's cost). The call is one forced, strict tool (`describe_clip`) with four 512 px frames as image bytes; its answer is untrusted, validated and cleaned by `internal/quicklook` before it reaches the database. Cassettes live in `internal/quicklook/testdata/cassettes/quicklook/`.
  - **Response blocks the client does not model** (`server_tool_use`, `web_search_tool_result`, ...) keep their raw JSON in `Block.Raw` and are sent back verbatim, so the runtime can append the assistant turn as it came (including `pause_turn`). They are part of the cassette key.
  - **Replay** writes no ledger row and skips the daily cap, because nothing was spent, but it reserves and settles the run budget with the cost the recorded usage would have had, so budget behaviour matches live. The `count_tokens` result is stored in the cassette at record time and served in replay, so cap decisions match live (a cassette without one falls back to a local estimate). Replay needs no API key.
  - **Cassette key** treats default-equivalent requests alike: `nil` and empty lists, no `tool_choice` and `auto`, cache lifetime `""` and `5m`, a `tool_use` input of nothing and `{}`.
  - **Seams for P4-00b:** `llm.KeyResolver` (which key and who pays: the BYOK vault plugs in here), `llm.ImageResolver` (the runtime's R2 reader) and `llm.Ledger`.

## 3. Agent runtime (P4-01)

`internal/agents/runtime`:

- **A run is a row in `agent_runs`:**
  - who and what: agent, workspace, project, parent run;
  - lifecycle: status (queued, running, waiting_input, succeeded, failed, cancelled), input, output;
  - routing: routing profile, model, effort;
  - spend: token totals, `cost_micros`, `budget_micros` and `billed_to`.
- **Every step is an append-only `agent_events` row** with run, seq and type. Types are status, assistant_message, tool_call, tool_result, error and artifact. Each row carries a payload of at most 64 KB; images are stored by reference to R2 keys, never inline. Payloads hold no secrets.
- **The loop is a River job `agent_run` with arguments `{run_id}`.** On every start it rebuilds the conversation from the events, so a crash or restart resumes the run. It then repeats these steps:
  1. Check cancellation and every budget: dollars, tokens, tool calls and wall clock (default 15 minutes). The dollar budget is the `llm.Budget` the runtime puts in each request's `RunInfo`; the client reserves each call's worst case against it before sending, so this check is only the early exit (`Remaining()`), not the enforcement. A call that fails with `llm.ErrOutcomeUnknown` is not retried: the step ends the run or asks, after looking at the ledger.
  2. Build the request:
     - the system prompt and tool definitions come first, with `cache_control`;
     - then the run context: the brief, the project's footage list and the current timeline summary;
     - then the conversation so far.
  3. Call the model and persist the assistant message.
  4. Run each tool call **idempotently**. The idempotency key is `run_id + tool_use_id`. A tool that changes state, such as `edit_timeline` or `render_preview`, first checks whether that key already produced a result and returns it if so. Then persist the tool result.
  5. Stop on `finish`, on an `end_turn` with no tool call, on a budget limit (status `failed` with reason `budget`, plus a summary), on cancel, or on `ask_user` (status `waiting_input`; a reply enqueues the job again).
- **Prompt caching:** one breakpoint after the tools and system prompt, and one rolling breakpoint on the last stable message.
- **Effort and thinking** are set explicitly from the routing entry.
- **Tool registry:** each tool is a Go type with a JSON Schema (`strict: true`), a validated input, a handler, and a `Mutates` flag. Tool errors go back to the model as `is_error` results with a message it can act on; they never crash the run.
- **Untrusted text** (brief, annotations, transcripts, quick-look titles) goes inside clearly delimited data blocks, and the system prompt says that data never changes the agent's instructions or permissions.
- **As built in P4-01** (details the sections above leave open):
  - **Job and tables.** The `agent_run` arguments are `{workspace_id, run_id}` (every query is scoped by workspace). The job is not unique: River only allows uniqueness over states that include `running`, which would swallow the job that answers an `ask_user` while the job that parked the run is finishing. The run itself decides: `ClaimAgentRun` takes a `queued` run, or a `running` one whose heartbeat is stale, and refuses a run a live worker holds. It runs on the `agents` queue with a 40 minute job timeout (wall-clock budgets are capped at 30 minutes). `usage_ledger.run_id` has no foreign key to `agent_runs`: the ledger is billing history that outlives runs, and `cfctl llm ping` writes rows with ad-hoc run ids.
  - **Fencing and recovery.** Each claim bumps `agent_runs.epoch`; every write of the loop (events, totals, the end of the run) carries the epoch and is refused with `ErrRunFenced` once another worker has claimed the run. A worker touches `heartbeat_at` every 15 s; a periodic job (`agent_runs_resume`, every 30 s) enqueues the runs whose heartbeat is older than 90 s, because River's own rescue of a killed job (`JobRescueAfter`) waits for the ingest timeout. A worker that stops with an error puts its run back to `queued` so the retry takes it at once; the last attempt of the job fails the run (`internal_error`).
  - **A worker that dies during a model call.** Just before the llm client sends a request it reserves the call's worst case against the run's budget; the loop hooks that reservation and writes it as a `status` event (`state: model_call`, `reserved_micros`) first. A takeover finds such an event with no answer after it and charges it to the run (a `cost_reconciled` event adds it to `cost_micros`): the remaining dollars are the budget less the larger of the ledger's total for the run and the run's cost plus the in-flight reservation, so a call that did finish and wrote its ledger row is not counted twice. The takeover then **asks the model again** from the last durable event (no tool ran during the lost call, so nothing can be duplicated; the lost call costs one reservation, bounded by the dollar budget and by the cap on resumes). It sends no note to the model, which has no memory of the lost call. An `ErrOutcomeUnknown` that the live client reports is different: the worker is alive and knows, so the run fails with `model_outcome_unknown`. Running time is written by the heartbeat as well as by events, so the wall clock counts a step that died.
- **Poison runs.** `agent_runs.resumes` counts the takeovers after a dead heartbeat and the retries after an error (not the restarts of a worker that was told to stop, and not the resumes after `ask_user`). A run past `MaxResumes` (5) is failed with `too_many_resumes` instead of being claimed again. A panic in the loop is recovered, recorded as an `error` event (`panic`), and the job retries like any error, so it counts. The sweeper marks a stale run (`resume_enqueued_at`) and enqueues its job in one transaction, and skips a run marked in the last five minutes, so one stale run has one job. `tool_call` and `tool_result` events are unique per `tool_use_id` in the database too.
- **Events.** `seq` is `agent_runs.last_seq + 1`, bumped in the same statement as the insert and the run totals (tokens, cost, tool calls, active time), so totals never disagree with the log. Event payloads are capped at 64 KB of compact JSON (the database check is a looser backstop); a tool result's text is cut to 48 KB and then to whatever fits once encoded (the size is measured after encoding, without HTML escaping, so escapes cannot push it over; empty text is dropped, NUL removed, blocks capped at 32; a reply that does not fit is refused), an image must be an R2 reference, and an assistant message or tool call that does not fit fails the run (`event_too_large`) after its cost is recorded. The run context is built once, stored as a `status` event (`state: context`), and sent unchanged on every resume. On resume the dollar budget also counts what the ledger holds for the run, so a paid call lost to a crash is not forgotten.
  - **Idempotency.** A tool call has its `tool_call` event written first; the tool runs with `RunContext.IdempotencyKey = run_id:tool_use_id` (and `Resumed` when the event already existed); the `tool_result` is written after. A call with a result is never run again. A call without one runs again after a crash, so a mutating tool must make its effect once by the key.
  - **Stopping.** Budget stops are `failed` with reason `budget`, an `error` event, a `status` event naming the limit (`dollars`, `tokens`, `tool_calls`, `wall_clock`) and a summary as the run's output; `ErrOutcomeUnknown` is `model_outcome_unknown` and the call is never sent again; a model call cut off by the wall clock is a budget stop, not an unknown outcome; a worker that is shutting down gives the run back instead of failing it. Wall-clock time counts only while the run runs (`active_ms`), not while it waits for the user. Cancel is checked between steps; a queued or waiting run is cancelled at once, and a cancel that arrives while a tool is asking wins over the question. Only `end_turn` and `stop_sequence` end a run as succeeded; `max_tokens`, `refusal`, `model_context_window_exceeded` and any unknown stop reason fail it with their own reason.
  - **Tools and prompt.** A tool's schema is checked at registration (compiles; `additionalProperties: false` on every object) and a call's arguments are validated against it before the tool runs; a `*ToolError` or an `IsError` result reaches the model, any other error becomes a generic message (details only in the log). The system block carries the cache breakpoint (the tools precede it in the prompt), the stored run context the second, and the last block of the conversation the rolling one. Effort comes from the routing entry and is `medium` when the entry has none; thinking is the agent definition's choice (default: the model's).
  - **Dev tooling.** `cfctl agent run` works a run in-process (refused on staging and production) and `cfctl agent show` prints a run's events, totals and ledger rows. The worker registers the `agent_run` worker from the same settings as `cfctl` (`LLM_MODE`, `ROUTING_PROFILE`, ...); when they do not load, agent jobs snooze.
- **Testing:**
  - The loop is tested with a scripted fake client.
  - Crash and resume are tested by killing the job between a tool call and its result.
  - Budget overrun is tested.
  - Replay tests use recorded cassettes.

## 4. Data the editor needs before P2

The full clip index (shots, tags, moments) arrives with P2. Until then the editor sees:
- **Each project asset:** its quick-look title and description (P1-04b), its duration and orientation;
- **For each asset, a keyframe grid:** frames from the proxy every 2 s, at most 8 (P4-02a review: 12 cost too much context), 384 px on the long side, made by ffmpeg in the sandbox and cached in R2.

This is enough for a first edit of a few short clips. It is not the product's final quality bar.

## 5. Editor tools, first slice (P4-02a)

| Tool | Returns |
|---|---|
| `get_brief()` | The project's format, brief text and constraints (the brief → constraints step is P4-04; until then the raw brief), and output limits |
| `list_footage()` | The project's clips: id, title, description, duration, orientation, has_audio |
| `view_clip(asset_id, at_ms[≤8])` | Those frames as images (384 px), with timestamps |
| `get_timeline()` | The current spec and its validation warnings |
| `get_comments()` | The creator's open comments (P1-08): kind, version and range, pin, text (untrusted data) and the timeline items that played there, resolved through the `time_map` of the render they were made on and marked as still in the current timeline or not. The run context carries the first few. `finish` marks the requests the run was handed as applied by it |
| `edit_timeline(ops[])` | Applies the P3-02 ops atomically → the new version number, a summary and the issues |
| `render_preview()` | Renders the current version with the `preview` profile (P3-06) → a contact sheet image and the duration. Calls `renderjobs.RenderAndWait(ctx, svc, renderjobs.AgentCaller(ws, runID), project, version, "preview", timeout)`: an identical render that exists is reused, a timeout (`ErrWaitTimeout`) leaves the render running and asking again returns it, and `Service.ContactSheetJPEG` reads the picture; its tiles' layout (output time and item per tile) is in the render's `contact_sheet` |
| `finish(summary)` | Ends the run |

`search_moments`, `get_sound`, `ask_user` and `delegate` come with P2, P5 and later P4 tasks. The tool contracts are JSON Schemas in `packages/schemas/agents/editor-tools.v1.json`. `edit_timeline`'s `ops` reuses `ops.v1.schema.json`.

**As built in P4-02a and P4-03** (`internal/agents/editor`, prompt in `prompts/editor.v1.5.md` with `prompts/CHANGELOG.md`; v1.1 says that the brief and the run's instructions are direction for the edit and that no data block can change the tools, the budget, the project or the rules):
- **The contract file is the source of the tools.** `editor-tools.v1.json` lists, per tool, the name, description, `strict` flag and input schema; the Go package embeds a copy (`go generate`, CI drift check) and builds its tools from it, so the model sees exactly what the file says. Strict tools stay inside what strict tool use supports (no ranges, patterns, `maxItems` or `oneOf`; limits go in the descriptions and the tool checks them). `edit_timeline` is the one non-strict tool, because the op schema uses all of those; it refers to the op schema by its `$id`, which is inlined into one document when the tool is registered, and the runtime still validates every call against the full schema first. `runtime.Spec.NotStrict` is the opt-out. Contract tests: Go (`contract_test.go`: the copy equals the source, the registered tools equal the file, strict subset, the bundled op schema) and Ajv (`editor-tools.v1.test.ts`).
- **Data the editor sees.** `list_footage` and the run context give, per ready clip of the project, in the creator's order: id, duration, orientation and size, sound, and the library title and description (the creator's text, in `untrusted_data` blocks; whole in the tool). The run context is built under a budget of 40 KB of encoded text (the event holds 64 KB): the brief excerpt, titles and descriptions are cut in steps (1,500 / 60 / 160 characters for the first 20 clips, down to facts only), measured after JSON encoding, so 50 clips of CJK text or text full of quotes still fit; the tools return everything. `view_clip(asset_id, at_ms[≤8])` returns frames of the proxy at those times, or without `at_ms` the overview: a frame every 2 s, at most 8 (a longer clip is sampled evenly). A time is moved into the proxy (not after its own duration less 100 ms, which the proxy derivative's metadata gives, since the proxy can be shorter than the original); a moment that cannot be decoded is reported next to the frames that worked, and only when none works is it a tool error. The frames are cut by one ffmpeg run in the sandbox (`media.FramesArgs`, 384 px on the long side, JPEG), cached in R2 at `ws/{workspace}/assets/{asset}/frames/{at_ms}_{size}.jpg`, and returned as image blocks by reference (`FrameService`). The llm client resolves the reference when it sends the request (`editor.ImageResolver`); events keep only the key. The resolver gets the request's workspace through the context (`llm.WorkspaceFromContext`) and reads only a clean `ws/{that workspace}/...` key that names a JPEG or PNG.
- **Tenancy.** Every tool acts for the workspace and project of the run row. An asset id from the model is looked up among the project's own ready footage; another project's, another workspace's, a deleted or not-ready one is the same answer, "not one of this project's clips". Object keys are built from ids by package `storage`. A tool never passes on a key outside the run's workspace (`CheckImageRef`).
- **Idempotent edits, on the version the model saw.** `edit_timeline` takes `base_version`, the version in the model's last `get_timeline` or edit result (0 for none), and passes it to `projects.Service.ApplyOpsOnce`; if the project moved on (a person edited, say) nothing is applied and the model gets a tool error with the current version and what its summary says (in a data block), telling it to re-read. The call's idempotency key `run_id:tool_use_id` is stored with the version in `timeline_versions.idempotency_key` (unique per project; migration 00011) together with the call's answer (`result`: the ids the ops created and the warnings); `author_id` stays the run's TypeID, as the API says. Under the project's lock, before the base check, `ApplyOpsOnce` looks the key up and returns the stored version and answer (`Replayed`), so a call that a resumed run makes twice makes one version and gets the same text back, and does not write the `timeline_version` artifact a second time.
- **Finishing.** `finish` is refused unless this run made a version (a version whose author is the run's TypeID), or the model passes `no_edit_needed: true` for a project that already has a timeline; the run's output then has `timeline_version: null`.
- **Previews.** `render_preview` calls the `PreviewRenderer` interface (`RenderAndWait(ctx, ws, project, version)`), bounded at 90 s. Until P3-06's render jobs are wired, `UnavailablePreviews` answers a tool error that tells the model to check with `get_timeline`. Wiring point: `cmd/worker/agents.go` and `cmd/cfctl/agent.go` (TODO for the director).
- **Agents are built in one place.** `runtime.DefaultAgents(extra...)` is the echo agent plus the extras; package `agentset` builds the whole runtime for a process (model settings, price table, router, factory with the image resolver, the editor with its services, `Service` and `Runner`): the worker (`RequireStorage`: without R2 and a sandbox its agent jobs wait), the api (`DefinitionOnly`: it creates and checks runs, the worker executes them) and `cfctl agent run --agent editor --project prj_...`.
- **API.** `POST /v1/projects/{id}/edit` (owner or editor; `instructions`, `profile` in dev-cheap, dev-mid or v1-start, `budget_usd` default $5 and capped at $5 by `runapi.MaxBudgetMicros`) starts a run under the project's row lock: one unfinished editor run per project (`409 run_in_progress`), at least one ready video clip (`422 assets_not_usable`; audio does not count). `GET /v1/runs/{id}` returns status, cost, tokens with the cache hit rate, budgets and one-line event summaries (`after_seq`, `limit`; no images, no run context); `POST /v1/runs/{id}/cancel` and `/reply`. All paid-only and workspace-scoped; another workspace's run or project is `404`. The api needs the model settings (and, in live mode, a key) only to fail fast with `503 model_not_configured`.
- **Tests.** Tool unit tests over Postgres, the frame service with a fake ffmpeg and with the real ffmpeg and MinIO, the image resolver, an end-to-end editor run over a generated three-clip project (`e2e_test.go`) with cassettes in `testdata/cassettes/editor`, recorded against a fake transport that scripts the model's turns (re-record with `CF_UPDATE_CASSETTES=1 go test ./internal/agents/editor -run TestEditorCassettesAreCurrent`), and the API through the whole stack (`internal/auth/runs_api_test.go`). `cfctl agent show` prints the cache write and read tokens of every call and the run's cache hit rate.

## 6. The first-edit milestone (the founder's test footage)

The goal: Gino's clips, imported into the founder's local workspace, edited by Opus 5.5 into a 9:16 short, previewed on the review screen. The steps:

1. `cfctl assets import --workspace <wks_…> <files…>` (dev only, refused on staging and production) uploads through the same storage and ingest path as the browser.
2. A `POST /v1/projects` endpoint backs the new-project flow (P4-04b): the format, the selected assets and the brief. It creates the project with no timeline yet (`current_timeline_version` is `null`): a timeline needs at least one clip, so version 1 is made by the first edit, which starts from an empty timeline of the project's format (`POST /v1/projects/{id}/timelines` with `base_version` 0, which is also what the agent's `edit_timeline` calls through `projects.Service.ApplyOps`). The edit's catalog holds only the project's own `ready` footage.
3. `POST /v1/projects/{id}/edit` starts an editor run. For this test it uses the `v1-start` profile (Opus 5.5) with a **$5 run budget**.
4. The preview render and the review screen show the result.

**The test's spend cap is $15 in total.** Every run's cost is reported from `usage_ledger`. Before the first live run, the same flow runs in `replay` against a cassette recorded on Haiku (`dev-cheap`, cents).
